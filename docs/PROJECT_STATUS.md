## Окружение и зависимости

Проект рассчитан на Python 3.12. Прямые зависимости описаны в
`pyproject.toml`, точные версии зафиксированы в `uv.lock`. Окружение создаётся
командой:

```powershell
uv sync --locked
```

Используются `osmnx`, `geopandas`, `shapely`, `networkx`, `pandas`, `numpy`,
`matplotlib` и `requests`. Для ноутбука в dev-группу включён `ipykernel`.

## Предварительная статистика зон

`src/transport_demand/zone_stats.py` распределяет объекты из
`data/osm/features.geojson` по зонам и формирует
`data/processed/zone_stats.csv`.

Текущий подход:

- жилой вес — площадь жилых зданий с учётом этажности;
- рабочий вес — площадь зданий рабочих категорий;
- объект относится к зоне по репрезентативной точке геометрии;
- для здания без `building:levels` принимается 5 этажей;
- магазины, офисы и другие точечные POI подсчитываются, но не влияют на
  рабочий вес, потому что `POINT_FLOOR_M2 = 0`.

Это относительные веса, а не подтверждённая численность населения или рабочих
мест. МФТИ, ДНПП и лицей пока не получили отдельных обоснованных абсолютных
объёмов.

## Предварительная модель спроса

`src/transport_demand/build_periods.py` создаёт
`data/processed/periods.json` для периодов `07:00`, `07:30`, `08:00` и
`08:30`.

Используются следующие допущения:

- внутренние поездки заданы заглушкой 4000 авто/ч;
- ворота `EXT_P02` используют значения P02A и P02B из `calibration.csv`;
- потоки `EXT_P03` и `EXT_P06` заданы примерно как 30% от P02;
- часовые значения делятся поровну между двумя получасами;
- внутренние отправления распределяются по жилым весам;
- внутренние прибытия распределяются по рабочим весам.

Поэтому `07:00` совпадает с `07:30`, а `08:00` — с `08:30`.

После округления суммы отправлений и прибытий расходятся:

| Период | Разница, автомобилей |
|---|---:|
| 07:00 | -0,02 |
| 07:30 | -0,02 |
| 08:00 | -0,01 |
| 08:30 | -0,01 |

`src/model.py` требует совпадения сумм с относительной точностью `1e-9`,
поэтому текущий `periods.json` не принимается моделью без исправления.

## Внешние ворота: оценка по населению соседних территорий
 
Часть ноутбука `notebooks/show_res.ipynb` оценивает относительный вес трёх ворот.
Результат пока не используется в `build_periods.py`.
 
Источник: слой НИУ ВШЭ «Муниципальные образования верхнего уровня России»
(метаданные датируют его апрелем 2023 года), поле `pop`; Москва представлена
внутригородскими округами, область — городскими округами.
 
Метод:
 
1. Берутся образования Москвы и Московской области, центр которых лежит вне
   области проекта (Долгопрудный, чей центр внутри области, исключается).
2. Каждое образование относится к ближайшим по прямой воротам (расстояние от
   центра образования до точки замера).
3. Учитываются образования не дальше 15 км.
4. Вес образования равен населению, делённому на квадрат расстояния
   (расстояние не меньше 1 км).
Результат последнего расчёта:
 
| Ворота | Население, чел. | Вес | Доля | Относительно P02 |
|---|---:|---:|---:|---:|
| P02 | 1 749 818 | 25 332 | 0,326 | 1,000 |
| P03 | 362 339 | 3 751 | 0,048 | 0,148 |
| P06 | 1 847 674 | 48 632 | 0,626 | 1,920 |
 
Интерпретация и ограничения:
 
- P02 остаётся якорём, так как для него есть измеренные потоки;
- вес P06 примерно вдвое выше P02; это согласуется с тем, что P06 является
  вторым концом Лихачёвского проезда рядом с МФТИ, но само число 1,9 пока не
  подтверждено калибровкой;
- для P03 по этому методу ближайших москвичей почти нет; его вес зависит от
  территорий севернее (вероятно, Лобня и Мытищи), а основной источник —
  части Долгопрудного за каналом и железной дорогой, для которых в слое нет
  отдельной цифры (весь округ — 117 778 человек);
- расстояния измерены по прямой, поэтому территории за каналом (например,
  Химки) могут быть отнесены к воротам не по реальным маршрутам;
- формула «население / расстояние²» выбрана как допущение, население не равно
  числу поездок.

## Математическое ядро

`src/model.py` реализует:

- поиск кратчайших путей алгоритмом Дейкстры;
- гравитационную OD-модель с обратной степенью времени `gamma = 2`;
- попеременную балансировку матрицы по строкам и столбцам;
- исключение внутрисзональных поездок;
- исключение внешнего транзита `external → external`;
- BPR с параметрами `alpha = 0,15` и `beta = 4`;
- пользовательское равновесие методом Франка—Вульфа;
- критерий остановки по relative gap `0,0001`;
- пересчёт машин за полчаса в автомобили в час;
- заполнение шаблона `flows_template.csv`.

Ядро проверено на небольшой условной сети и на ней сходится. Городской запуск
не выполнялся, потому что отсутствует `data/processed/model_input.json`.

Для полного входа нужны четыре блока:

- `edges` — модельные направленные рёбра;
- `zones` — внутренние зоны и внешние ворота с узлами подключения;
- `periods` — сбалансированный спрос;
- `point_edges` — привязка всех 30 направлений к рёбрам.

После появления входа запуск выполняется командой:

```powershell
uv run python -m src.model data/processed/model_input.json
```

Результат должен появиться в `outputs/flows.csv`.
