# Макромодель транспорта Долгопрудного

Проект курса "Транспорт большого города". Считаем автомобильные потоки
континентальной части Долгопрудного с 07:00 до 09:00 по четырем получасам.

## Что работает

Собран `data/processed/model_input.json`: 440 направленных ребер, 7 внутренних
зон и 3 внешних ворот, спрос на четыре периода и привязки 30 направлений замеров.
Из него воспроизводится первый `outputs/flows.csv` с 120 значениями в авто/ч.
Все четыре расчета сходятся с relative gap меньше `0.0001`.

Это стартовая версия без калибровки. Внутренний спрос пока равен 4000 авто/ч,
а P03 и P06 используют прежние заглушки. Получасы внутри одного часа одинаковые.
На части улиц модель дает нули; подключения зон и распределение спроса надо
дорабатывать. Состояние и ограничения описаны в
[PROJECT_STATUS.md](docs/PROJECT_STATUS.md), следующие задачи в
[ROADMAP.md](docs/ROADMAP.md).

## Запуск с сохраненными данными

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/).
Все исходные CSV курса и снимок OSM уже находятся в репозитории.

```sh
uv sync --locked
uv run python -m src.build_model_input
uv run python -m src.model data/processed/model_input.json
uv run python -m unittest discover -s tests -v
```

Сборщик сам пересчитывает спрос по текущему `zone_stats.csv`, проверяет баланс,
маршруты между зонами и допустимость OD-матрицы. Повторная загрузка OSM не нужна.

Если меняются здания или границы зон, сначала пересчитайте статистику:

```sh
uv run python -m src.transport_demand.zone_stats
```

После этого снова выполните сборку и расчет. Отдельно обновить `periods.json`
можно командой `uv run python -m src.transport_demand.build_periods`.

## Параметры и результаты

- `data/input/model_config.json`: скорости по умолчанию, емкость полосы,
  привязки направлений к ребрам и состав внешних ворот
- `src/transport_demand/build_periods.py`: стартовые объемы поездок
- `data/processed/model_input.json`: полный вход для `src/model.py`
- `data/processed/point_bindings.csv`: выбранные ребра, направление,
  расстояние до точки и до границы территории
- `data/processed/point_bindings.geojson`: геометрии выбранных участков для QGIS
- `data/processed/zone_connections.csv`: подключения семи зон и времена примыканий
- `outputs/flows.csv`: первый расчет потоков, авто/ч

Спрос внутри модели измеряется в машинах за полчаса. Пропускная способность
задается в авто/ч. При выгрузке число машин за полчаса умножается на два.
Часовой замер сравнивается со средним двух получасовых интенсивностей.

## Как собран вход

Скорость берется из OSM с учетом направления. Если тега нет, используется
скорость для класса дороги из конфига. Для объединенных участков берем
минимальную известную скорость. Направленные полосы имеют приоритет;
общее число полос двусторонней дороги делится между направлениями. При
неизвестном числе полос берем одну на направление, емкость полосы 1500 авто/ч.
Это допущения для старта, их еще нужно проверять и калибровать.

Внутренние зоны подключаются к ближайшему к репрезентативной точке зоны узлу
внутри ее полигона и основной сильной компоненты графа. Время примыкания
считается по прямой со скоростью 20 км/ч. Для ворот дорожные ребра разделяются
в створе замера; все исходные физические маршруты сохраняются. Внутризональные
поездки и корреспонденции между внешними воротами отключены в ядре модели.

Проверки покрывают направления A/B, баланс OD, сохранение маршрутов при
добавлении ворот, сохранение числа машин на узлах, сходимость и выгрузку CSV.

## Остальные материалы

В `data/osm/` лежат снимки OSM, граф и объекты застройки, в `data/hse_data/`
слой населения ВШЭ. В `notebooks/show_res.ipynb` есть исследовательские расчеты
весов внешних ворот. Эти веса пока не используются в модели. Ноутбук остается
исследовательским: для воспроизведения `flows.csv` он не нужен.

Карта районирования пересобирается командой:

```sh
uv run python -m src.visualization.view_project_boundary --export-only
```
